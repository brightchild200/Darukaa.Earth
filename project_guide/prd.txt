1. Product Overview

Darukaa.Earth is a geospatial data analytics platform that enables users to create, manage, visualize, and analyze carbon and biodiversity projects geographically.

The platform combines:

Project management
Interactive geospatial mapping
Polygon-based site creation
Environmental metrics
Time-series analytics
Project-level KPIs

The primary experience is:

Create Project
      ↓
Add Geographic Sites
      ↓
Draw Site Polygon
      ↓
Store Polygon in PostGIS
      ↓
Select Site
      ↓
View Site Intelligence
      ↓
Analyze Environmental Performance
2. Problem Statement

Carbon and biodiversity projects are inherently geographic.

A traditional dashboard can show:

Carbon captured
Biodiversity score
NDVI
Project performance

but doesn't naturally answer:

"Where exactly is this project happening, and how is each geographic site performing?"

Darukaa.Earth combines spatial context + environmental analytics in one interface.

3. Product Goals
Primary Goals
Allow users to create environmental projects.
Allow multiple geographic sites per project.
Allow users to draw site boundaries directly on a map.
Persist geographic boundaries using PostGIS.
Display all project sites on an interactive map.
Allow users to select a site and inspect its performance.
Visualize environmental metrics over time.
Provide a polished, intuitive dashboard experience.
Secondary Goals
Demonstrate production-quality architecture.
Demonstrate proper geospatial database usage.
Demonstrate CI/CD and code-quality automation.
Provide realistic environmental demo data.

Site Analytics

As an admin, I want to select a site and see its environmental performance over time.

Project Overview

As an admin, I want to see project-level KPIs so that I can quickly understand overall performance.

6. Projects Table
CREATE TABLE projects (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),

    owner_id UUID NOT NULL
        REFERENCES auth.users(id)
        ON DELETE CASCADE,

    name VARCHAR(200) NOT NULL,

    description TEXT,

    project_type VARCHAR(30) NOT NULL
        CHECK (
            project_type IN (
                'Carbon',
                'Biodiversity',
                'Mixed'
            )
        ),

    status VARCHAR(30) NOT NULL DEFAULT 'active'
        CHECK (
            status IN (
                'draft',
                'active',
                'completed',
                'archived'
            )
        ),

    start_date DATE,
    end_date DATE,

    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
7. Sites Table

This is the most important table technically.

CREATE EXTENSION IF NOT EXISTS postgis;

Then:

CREATE TABLE sites (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),

    project_id UUID NOT NULL
        REFERENCES projects(id)
        ON DELETE CASCADE,

    name VARCHAR(200) NOT NULL,

    description TEXT,

    geometry GEOMETRY(POLYGON, 4326) NOT NULL,

    area_ha NUMERIC(14,4),

    status VARCHAR(30) NOT NULL DEFAULT 'active'
        CHECK (
            status IN (
                'active',
                'inactive',
                'pending',
                'archived'
            )
        ),

    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

Spatial index:

CREATE INDEX idx_sites_geometry
ON sites
USING GIST (geometry);

This is important for geospatial queries.

8. Site Metrics
CREATE TABLE site_metrics (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),

    site_id UUID NOT NULL
        REFERENCES sites(id)
        ON DELETE CASCADE,

    metric_date DATE NOT NULL,

    carbon_tco2e NUMERIC(14,2),

    biodiversity_index NUMERIC(6,4),

    ndvi NUMERIC(6,4),

    projected_credit_usd NUMERIC(16,2),

    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    UNIQUE(site_id, metric_date)
);

Index:

CREATE INDEX idx_site_metrics_site_date
ON site_metrics(site_id, metric_date);

11. Area Calculation

Don't trust the frontend to calculate area.

Calculate it on the backend/database.

SELECT
    ST_Area(geometry::geography) / 10000
AS area_ha
FROM sites;

Why?

Because:

Frontend area
      ❌
Potentially inaccurate

PostGIS area
      ✅
Geospatial calculation

15. Should You Use Supabase?
Yes, but choose one of these two approaches.
Architecture	Speed	Challenge Alignment	Complexity
React → Supabase	⭐⭐⭐⭐⭐	Good	Low
React → FastAPI → Supabase DB	⭐⭐⭐⭐	Very strong	Medium
React → FastAPI → self-hosted PostgreSQL	⭐⭐⭐	Strong	Higher

For 15 hours, I recommend:

React + FastAPI + Supabase PostgreSQL/PostGIS

Why?

You get:

Supabase
├── PostgreSQL
├── PostGIS
├── Auth
├── Database dashboard
├── Hosted infrastructure
└── Easy deployment

+

FastAPI
├── API layer
├── Validation
├── Business logic
└── Analytics aggregation

This lets you demonstrate actual backend engineering rather than making the frontend talk directly to the database.

16. One Important Caveat

The challenge explicitly asks for:

Python with Flask/Django/FastAPI

So don't present:

React → Supabase

as your entire backend if the judges expect a Python backend.

Instead:

React
  ↓
FastAPI
  ↓
Supabase PostgreSQL
  ↓
PostGIS

Use Supabase primarily as your managed PostgreSQL/PostGIS + Auth/infrastructure layer, while FastAPI remains your application backend.

That is a very defensible architecture for the challenge.
